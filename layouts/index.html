No libc of its own,
so there is nowhere it cannot run.

The pkgx world rebuilt in pure CGO_ENABLED=0 Go: a runtime that runs packages on the fly, an installer that mirrors the reference CLI, and the bottle backend they share. The reference tools shell out to pkgx + deno + curl + openssl + xz — about 515 MB of runtime closure. These replace all of it with single ~9 MB static binaries that need no libc at all, so they run on a literally empty FROM scratch image and materialise real packages there. BSD-3-Clause.

Install

One line, and it names a version on purpose.

It downloads the static binary for your os/arch from a named GitHub release, verifies it against that release's SHA256SUMS, and puts it on your PATH. A line copied today and the same line copied in six months install the same bytes — and a bad release does not reach everyone who happens to install that hour.

Tracking releases, and updating

Write latest where the version goes — which is also what a bare | sh has always done. Re-running is the updater: it skips the download when the target version is already installed, and PKGM_FORCE=1 reinstalls anyway. Go users: go install github.com/go-pkgx/pkgm@latest.

Why go-pkgx

A package manager that owns its own environment.

Every dependency a packaging tool shells out to is a dependency the packages it installs have to coexist with. Removing them is not tidiness — it is what makes an empty image a valid target.

Finding things

A tree you can walk, offline, in an empty image.

nix, guix and spack all let you browse what exists before you install it. Here the same thing works where none of them run: a single static binary, a catalogue cached as one file, and no network after the first fetch. <TAB> answers in 7.6 ms because nothing on that path opens a socket.

pkgx — zsh
# once, with a network. Then never again.
$ pkgx catalog update
1908 project(s) → ~/.pkgx/catalog/linux-x86-64.json

# a namespace lists what it CONTAINS, a package what it NEEDS
$ pkgx ls --tree curl.se
curl.se — 8.17.0  ✓
  curl.se/ca-certs  2026.09.25  ✓
  doxygen.nl  (no bottle here)
  openssl.org  3.6.0  ✓ 3.5.1

# you know the command, not the package
$ pkgx search rg
crates.io/ripgrep                        rg  14.1.1
🌳

A node has two kinds of thing under it

gnu.org contains gnu.org/bash because of how it is named; curl.se has openssl.org under it because of what it needs. nix and guix keep the two in separate commands; here the node decides, because the person typing already knows which they named.

⌨️

The binary answers <TAB>

Spack generates a completion file and commits it; guix hand-writes one per shell. Both then need a check that it still matches. Nix has the binary answer, and so does this — because what is being completed is the registry, which changes without the binary changing, and because there is no completion framework in an empty image.

🔭

Everything is named; what is here is marked

A catalogue is published per platform: 537 of 1908 projects have no bottle for darwin/aarch64. Dropping those names would say they do not exist, which is false. Marking them says what to build next.

🖥️

And a full-screen browser

pkgx browse walks it with the arrow keys, / searches, space pins — and q prints what you pinned on stdout, so pkgx +$(pkgx browse) composes. Without a terminal it prints the tree and exits.

Reproducibility

The same build, later.

The same pantry commit resolved tcl to 9.0.4 and then to 9.1.0 four hours apart, because a recipe asks GitHub at resolution time. bk lock writes down what a set means today — Spack's shape: a Merkle hash over the platform, the version and the parsed recipe, so a recipe edited under a pin is visible where a version alone would say nothing.

📌

Every pin is a root

pkgx --lock f.hcl runs exactly those versions and bk factory --lock f.hcl builds them — not just the lock's own roots, so a transitive dependency cannot move underneath. A set that will not resolve exactly fails, as cargo's --locked does.

🧭

It knows where it was taken

A lock records its platform and refuses to be honoured elsewhere, by name. The versions a platform carries are not the versions another has, and failing late inside a resolver would blame a version instead of the lock.

Environments and HPC

A module system, without Lmod.

A module system does two things: it resolves what a package needs, and it edits your shell. pkgx +a +b already did the first. pkge does the second — a front-end shaped like Lmod's, over pkgx's own resolution, with no Lua interpreter and no modulefile tree. It ships inside the pkgx binary; there is nothing else to install.

pkge — zsh
$ eval "$(pkgx env init)"          # in a profile
$ pkge load stedolan.github.io/jq
$ command -v jq
~/.pkgx/stedolan.github.io/jq/v1.8.2/bin/jq
$ pkge unload stedolan.github.io/jq
$ command -v jq
/usr/bin/jq                        # back, exactly as it was
↩️

Unloading is exact

Because loading never edits incrementally: it restores the environment it first saw and recomposes from the whole spec set. So unload b after load a b c leaves precisely what load a c would have — whatever order things happened in.

🤝

It defers to a real Lmod

Where a site already runs one, publish modulefiles — pkgx --modulefile +openmpi.org@5 — and let the site's own Lmod load them, so conflicts, hierarchies and spider keep working.

🚫

And refuses to shadow it

pkgx env init --module defines module and ml only where there is no Lmod. Two implementations answering one command is how a support ticket becomes unanswerable.

Provenance

A signed, attested package registry.

The org runs its own bottle registry at ghcr.io/go-pkgx/packages. A pure-Go factory builds pkgx pantry recipes with bk, a CGO-free re-implementation of brewkit, and publishes through two channels: the signed OCI registry and a GitHub Pages pkgx-dist mirror.

🔏

Fail-closed by default

Each bottle carries, as OCI referrers, a CycloneDX SBOM, an in-toto SLSA provenance statement and a cosign-style signature verified against a pinned key. On install PKGX_VERIFY=1 refuses an unsigned or badly-signed bottle.

📥

What went in, not only what came out

The provenance records the source archive's SHA-256 (or a git commit) as well as the artefact. Over half this pantry builds from tarballs GitHub generates on request rather than stores, so for those it is the first stored record they have ever had.

🧱

Built where nothing leaks in

Linux builds run inside a FROM-scratch rootfs staged from bottles — no distribution libc and no distribution compiler take part. The output carries its PT_INTERP into the pkgx prefix and no distribution strings at all.

🔑

No long-lived credential

Publishing uses the workflow's native GITHUB_TOKEN, never a personal token, and every (project, version, platform) already present is skipped, so the catalogue grows progressively rather than being rebuilt.

Packaging that ships like Go.

No cgo, no interpreter, no runtime to install first. One static binary per job, a backend they share, and bottles that say where they came from.
